# 对抗审查规则集

供 Step 7 使用。目标不是挑刺，是找「一戳破、整个结构就塌」的根本缺陷。V2 流程中，对抗审查必须同时攻击策略风险和交付矛盾。

## 一、Steelman 先行（防稻草人）

审查前，先把自己方案说到最强版本——说到「拥护者会点头说：对，这就是我的方案」。再攻击这个最强版。

**禁止**：攻击一个弱化版/曲解版，然后宣布自己赢了。那是自嗨，不是审查。

**检验**：反证打出来后，方案提出者能不能说「这不是我的意思」？能说，说明你打了稻草人。

## 二、攻击角度清单（15 个）

每个视角一句攻击话术，逐条过一遍，别跳。**每条反证必须标注依据**：是事实（引用户口碑/数据）还是推测，推测必须标「待验证」，不许凭直觉口嗨。

| # | 攻击视角 | 攻击话术 |
|---|---|---|
| 1 | 凭什么来 | 受众有非来不可的理由吗？ |
| 2 | 传播不出去 | 有值得截图转发的点吗？社交货币在哪？ |
| 3 | 预算错配 | 钱花在了不产生结果的地方吗？ |
| 4 | 执行翻车 | 天气/供应商/现场事故，哪个环节会崩？ |
| 5 | 合规风险 | 报批、消防、食品酒类、广告法、版权，漏了吗？ |
| 6 | 效果难衡量 | 热闹完能归因到结果吗？还是自嗨一场？ |
| 7 | 动机错配 | 这活动满足的是真需求，还是假象？ |
| 8 | 创意自嗨 | 甲方觉得好，受众无感，怎么办？ |
| 9 | 时机错配 | 时间窗口差吗？跟竞品扎堆了吗？ |
| 10 | 资源错配 | 人力/物料/时间够吗？谁来做？ |
| 11 | 假设不成立 | 哪些 Soft/Assumption 被当成了 Hard？ |
| 12 | 二阶效应 | 会不会引发负面舆论、后续麻烦？ |
| 13 | 前提不成立（判死唯一出口） | 这个活动本身一定要办吗？不办活动能不能达成目标？有依据地命中 → 给出不建议办原活动的理由及符合真实目标的非活动替代方向，沿用 Step7 暂停等待用户选择；不自动生成替代全案。后续按下文收敛原则和主文件 Step9 处理，原活动记“需重做关键模块”并保留前提不成立的说明，不把替代方向或多数赞成误记成原活动可上交 |
| 14 | 维度冲突 / 缺失 | 确认的维度全被承载了吗？有没有显眼维度挤掉了其他维度（如促销挤掉品牌演绎）？维度之间打架了吗？ |
| 15 | 推导路径定位错 | 推导路径（七状态→对象→形态→时空）定位对了吗？「这个活动真的是身份确认，还是其实想卖货（行为）」？类型定位错了，方案全错。 |

## 三、V2 交付一致性攻击

策略攻击之后，必须追加交付攻击。正式、大型、To B、赞助、政企、文旅、老板过会项目不能跳过。

| # | 攻击视角 | 攻击话术 |
|---|---|---|
| D1 | 主叙事空心 | 去掉形容词后，主叙事还有真实动作和证据支撑吗？ |
| D2 | 中国语境失配 | 这个表达在老板、政府、客户、用户面前会不会尴尬、失礼、掉价、口号化？ |
| D3 | 行为改变断裂 | Step 2 定义的目标行为，现场机制真的能推动吗？ |
| D4 | 报名目标错配 | 邀约池、报名目标、到场目标、场地容量和餐饮数是否一致？ |
| D5 | 预算体验错配 | 预算押注是否支撑主场面和核心体验？钱是否花在不产生结果的地方？ |
| D6 | 赞助履约风险 | 承诺给赞助商的权益是否有资源、授权、证明材料支撑？ |
| D7 | 数据采集失败 | KPI 是否有采集点、负责人、工具和失败备份？ |
| D8 | 关键路径冲突 | 审批、设计、制作、搭建、彩排是否存在依赖冲突？ |
| D9 | 会中设计无效 | 峰会/圆桌/闭门会是否只排议程，没有推动认知、关系或销售？ |
| D10 | 事实来源不足 | 预算、案例、数据、政策是否被写成事实但没有证据等级？ |
| D11 | 需求被模板吞掉 | 按原 brief 逐条定位，哪些核心要求只有同名章节却没有实际内容？哪些愿望被偷换成硬约束或被惯例删除？ |
| D12 | 内容与串联空缺 | 不看策划口头说明，观众到底看什么/做什么、如何开始结束、为什么接下一单元？系列是否只是换名复演？ |
| D13 | 文件交付虚假 | Step7检查本阶段承诺的内容底稿是否存在、最终文件要求和生成能力是否明确；不把尚未到Step8/9的导出件判漏交。Step8/9及已声称交付的文件须检查真实存在、内容与可用性，不能以目录、提示词、索引或改名文件抵交。 |
| D14 | 用途与成熟度错位 | 概念案是否被执行大表挤空，执行稿是否只有概念名词？创作拟案是否被写成资源锁定、制作完成或审批通过？ |
| D15 | 跨文件断裂 | 概念、方案、ROS、脚本、视觉、预算的单元内容、数量、时长、权益、版本与资源状态是否一致？ |
| D16 | 接手仍需重写 | 主创、设计、主持、供应商或传播团队能否据约定深度接手？Step7核对内容和接手条件，Step9对实际成品执行代表任务；不能以几个名称、截图表格或不可编辑文件抵交约定工作件。 |

按本次交付用途解释 D11-D16：概念评审不强求施工图，传播规划不冒充发布成品，复盘缺数据不能编成果。覆盖检查依据 `proposal-schema.md` 的需求追踪，攻击应给出具体要求/文件位置、事实或待验证依据，不因追求“大而全”增添用户未要的文件。

## 四、收敛 + 严重度排序

- **多个角度独立打中同一弱点** = 关键发现，必改。
- **孤立冷门洞察**：先核对证据与影响；只有与本次用途无关或缺乏依据且不影响关键判断时才可搁置。有充分证据的关键失败，即使只有一个视角发现也必须修复。
- **根本缺陷**：优先找那个「一戳破整个结构就塌」的主要致命假设，避免罗列空泛意见；其他独立的关键失败仍逐项处理，不能为了只留一个而删掉。

输出排序：从「能毁掉整个活动」到「锦上添花」降序排。

## 五、补救方法

每条高严重度缺陷，给**可执行的修法**，不是「注意一下」：

- ❌ 「注意现场安全」 → 空话。
- ✅ 「增配 2 名持证安保 + 提前 48h 消防预检 + 应急预案 A/B」 → 可执行。

修法要能落到：加什么机制、换什么动作、删什么环节、补什么资源。

内容/交付缺陷优先补齐实际正文、规则、脚本、衔接或真实文件，不能用增加形容词、装饰图、目录、页数和审计表当修复。未知外部资源与已授权创作分开处理：继续完成可创作部分，同时列明事实缺口及影响。数量、规格、安保资质和时间要求须有本项目依据；上面的示例数字不是适用于所有活动的现场标准。

**判词规则（强制）**：每条攻击的默认落点是「怎么让它可行」——给修法、给预案、给降级版。风险类缺陷 = 加预案，不是枪毙创意。最有创意的想法第一眼永远最不可落地，对抗是把它修成能落地，不是把它杀了。

**唯一例外（攻击13）**：只有活动前提不成立、活动并非达成目标的合适方式时，才建议“不办原活动”，并给有依据的非活动替代方向。按本步原有暂停点等待用户决定，不能把建议当成新委托已确认。后续Step9沿用主文件判词：原活动记“需重做关键模块”，具体注明前提不成立及“不建议办/转非活动”的建议；不能为了进入终审而虚构Step8活动全案。其他可修风险仍给修法、预案与降级，不用此出口规避内容开发。

## 六、审查终局三问

1. 修完后，那个根本缺陷还成立吗？
2. 用户还没确认，你能替用户下这个判断吗？（不能）
3. 还有没有「大家礼貌性不提」但很致命的问题？

用最强反方再核对修复证据：原brief在当前阶段承诺的关键内容是否写出、已声称完成的文件是否存在、读者能否完成指定判断或动作、执行者能否据约定深度接手。按D13区分Step7底稿审查和Step9成品验收。任一影响本次用途的关键失败未修复，评分不能抵消，也不能判当前可上交。“小修后上交”表示修改与复核尚未完成，不能提前宣布交付通过。

## 七、内部记录格式

| 严重度 | 攻击点 | 依据/证据等级 | 为什么会毁掉方案 | 修法 | 失败降级 |
|---|---|---|---|---|---|

每条高严重度缺陷必须给修法和失败降级。只写“注意”“优化”“加强”判为无效审查。给用户的 Step 7 阶段输出只展示最高风险和需要拍板的修法；完整攻击表进入思考过程文件。
